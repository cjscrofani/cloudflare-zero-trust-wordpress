# Independent audit of 2.0.0 (2026-10-23)

> **Resolution (same day):** every Blocker, High, Medium and Low item below has been
> addressed in the working tree. Verification: `php -l` clean on all files; a scripted
> suite against the local dev site (`.dev`) covering encryption idempotency, legacy
> decode, sanitizer field preservation, enum whitelisting, activation-path migration,
> import/export, CSV escaping, trusted-proxy IP logic, role re-sync, login start
> (random state/nonce, HttpOnly SameSite=Lax cookie), callback rejection without the
> cookie or with a wrong/replayed state, primary-mode bypass attempt (302 to the start
> URL, no session cookie), lost-password refusal, backup-code login in primary mode,
> and the failure-only rate limiter ignoring spoofed CF-Connecting-IP. The sandbox was
> upgraded in place from a 1.x-encoded secret and re-encoded correctly. Remaining
> manual check: one real Cloudflare login round trip on the sandbox after deploy.

Three reviewers with no prior exposure to this branch read the full delta from the 1.0.4
release (`93f92c6`) plus the uncommitted working tree: one for security, one for
correctness, one for docs and release readiness. Overlapping findings were merged.
Every High and the top Medium items were re-verified by hand against the code before being
written here. "Pre-existing" means the bug ships in 1.0.4 today.

Severity key: **Blocker** = must fix before tagging 2.0.0. **High** = fix in 2.0.0 or a 2.0.x
within days. **Medium** = fix soon. **Low/Info** = backlog.

## Blockers

### B1. Primary mode is bypassed by `?cfzt_callback=1` — pre-existing
`includes/class-cfzt-auth.php:402-423`. `maybe_disable_wp_login` (authenticate, prio 30)
only redirects when `$_GET['cfzt_callback']` is absent. `handle_callback` ignores requests
without `code` and `state`, so the bare parameter switches the control off while core
password auth (prio 20) still runs. Attacker POSTs `log`/`pwd` to
`wp-login.php?cfzt_callback=1` and password login works. Lost-password is only hidden by CSS.
**Fix:** gate on `code`+`state` being present (or move callback handling off `authenticate`
entirely), and block `lostpassword`/`register` server-side in primary mode.

### B2. OIDC `state` is one shared nonce for all anonymous visitors — pre-existing
`class-cfzt-auth.php:107-108, 153-166`. `wp_create_nonce('cfzt_auth')` for uid 0 is
identical for everyone for up to 12 h and is printed in the login button href. Verification
is "does a transient with this name exist", with no per-browser binding and no OIDC `nonce`.
Consequences: login CSRF (victim lands in the attacker's account), and a functional race
(two concurrent logins share one transient; the second fails "Invalid Authentication
Request").
**Fix:** random per-flow state stored in a short-lived HttpOnly cookie (or transient keyed on
a cookie value); add PKCE or an ID-token `nonce` check.

### B3. Manual re-install of 2.0.0 skips the SAML migration and leaves a dead UI — new
`includes/class-cfzt-plugin.php:329` (`activate()` writes `cfzt_version = 2.0.0`) and
`:157-170` (`maybe_upgrade` then sees versions equal). Deactivate → delete → upload →
activate (normal for a GitHub-distributed plugin) leaves `auth_method='saml'`. Then:
`templates/admin-page.php:612,753` hide both wizard panels, `class-cfzt-admin.php:900` makes
Test Connection report success without checking, and a SAML+primary site gets a blank login
page (`class-cfzt-login-ui.php:72-88` hides `#loginform`, no button renders).
**Fix:** run the upgrade routine from `activate()` (or don't touch `cfzt_version` there when
settings already exist), hook the migration on `init`/`plugins_loaded` rather than only
`admin_init` (F14), and delete the `$auth_method` gates in template and admin.

### B4. Saving the Advanced form wipes role mapping, domain restrictions and redirects — pre-existing, now the default path
`class-cfzt-admin.php:259-283` only copies those keys when present in `$input`, with no
fallback to the stored option (the provenance keys at 290-297 do have one). The Advanced
form renders none of those fields, and since 2.0.0 Advanced is the default view once
configured. Toggle "Enable logging" → Save → role mapping gone, silently.
**Fix:** same preserve-from-existing pattern used for the provenance keys.

### B5. Release packaging will ship `.dev/` and extract into the wrong folder — new
`.gitattributes:76` says `/dev export-ignore`; the directory is `.dev`. `git archive HEAD`
confirms `.dev/bin/dev` and `.dev/docker-compose.yml` are included. No past release has an
asset, so `class-github-updater.php:210-228` falls back to the tag zipball, whose top folder
is `cloudflare-zero-trust-wordpress-2.0.0`, and there is no `upgrader_source_selection`
rename. WordPress will install into a new folder and the old active path disappears.
**Fix:** `.dev export-ignore`; attach `cloudflare-zero-trust-login.zip` built with
`git archive --format=zip --prefix=cloudflare-zero-trust-login/ v2.0.0` (or add the
source-selection rename); run a real 1.0.4 → 2.0.0 update on the sandbox before tagging.

### B6. Plugin header lacks `Requires at least` / `Requires PHP` — pre-existing
`cloudflare-zero-trust-login.php:2-10`. The updater advertises PHP 5.6 / WP 4.7 as
fallbacks; the code needs 7.1+ (`: void`, `??`). Activation checks 7.2/5.0 but don't run on
update. **Fix:** add `Requires at least: 5.0` and `Requires PHP: 7.2`.

## High

### H1. Settings import and the SAML migration double-encrypt the client secret
`class-cfzt-admin.php:1694,1725` (import, pre-existing); `class-cfzt-plugin.php:203`
(migration, new). Both encrypt and then `update_option`, which runs `sanitize_settings()`
and encrypts again. After an import, every token exchange fails; "Test Connection" still
passes because it only checks non-empty. The provisioner dodges this via `has_filter()`,
which is correct but fragile. **Fix:** make the sanitizer idempotent (mark encrypted values)
or route every programmatic write through one path that bypasses it.

### H2. Rate limiter trusts attacker-controlled headers — pre-existing
`class-cfzt-security.php:146-165`. `CF-Connecting-IP`, `X-Forwarded-For`, `X-Real-IP` are
trusted unconditionally. If the origin is reachable directly, rotating the header gives
unlimited backup-code guesses (each costs up to 10 bcrypt checks), and spoofing a victim's IP
locks them out of OIDC login for 5 minutes (counter increments before state validation at
`class-cfzt-auth.php:139`). **Fix:** only trust `CF-Connecting-IP` when `REMOTE_ADDR` is in
Cloudflare's published ranges, or make trusted proxies an opt-in setting.

### H3. Provisioning with `CFZT_CLIENT_SECRET` defined discards the new secret forever — new
`class-cfzt-provisioner.php:260-283`, `class-cfzt-admin.php:1000-1008` (`protect_constants`).
The constant wins on save, the AJAX response omits the secret by design, and the warning at
`provisioner.php:461` says it "is shown only once" when it is never shown. Result: a live
Access app whose secret nobody has. **Fix:** refuse to provision while the constants are
defined, or return the secret once in exactly that case.

### H4. Role mapping cannot work on provisioned apps, and only runs at first login — pre-existing
Auth request scope is `openid email profile` (`class-cfzt-auth.php:123`); the provisioner
grants `groups` on the app (`class-cfzt-provisioner.php:224`); `class-cfzt-user-helper.php:211`
reads a `groups` claim that is never requested. `determine_user_role` is only called from
`create_user`, so existing users are never re-mapped, contrary to the tooltip at
`templates/admin-page.php:878`. Same first-login-only limitation applies to
`email_domain_restrictions` (`user-helper.php:29`). **Fix:** add `groups` to the auth scope
(and README:124); re-evaluate role and domain rules on every login, or change the UI text.

### H5. Wizard review step throws a ReferenceError — new regression
`templates/admin-page.php:1336` reads `authMethod`, which was deleted with the method radio.
`populateReview()` throws and the Configuration Summary stays empty. Line 1340 still emits
the SAML string "SSO Target URL configured". Not a stuck state (Save is shown first).

### H6. After a successful provision, stale forms can overwrite fresh credentials — new
`templates/admin-page.php:1945-1964`. "Switch to Advanced Mode" and wizard "Next" remain
active with render-time (empty) values; Save then blanks `team_domain`/`client_id`/
`client_secret`. **Fix:** reload automatically on success or disable both forms until reload.

## Medium

- **M1. Backup codes are unreachable in primary mode.** Prio-30 redirect fires before the
  prio-40 backup-code filter; the link is also hidden (`class-cfzt-backup-codes.php:432`). The
  emergency path only works when the password form is available anyway. (pre-existing)
- **M2. Any `edit_users` holder can mint backup codes for any CFZT user, returned in
  plaintext.** `class-cfzt-backup-codes.php:193-208` checks the primitive `edit_users` rather
  than `edit_user` for the target. (pre-existing)
- **M3. Client secret is rendered in plaintext** in the settings page `value` attribute and in
  export JSON (`class-cfzt-admin.php:449-452, 1613-1616`; `admin-page.php:789`). Encryption
  at rest only protects against DB-dump readers. (pre-existing)
- **M4. API client labels any HTTP 400 as a bad token.** `class-cfzt-cloudflare-api.php:260`.
  A validation 400 (e.g. `session_duration` of `7d`, which `resolve_session_duration` accepts
  but Cloudflare does not; or an `http://` redirect URI) tells the user to re-create tokens.
- **M5. Esc key dismisses the SAML notice permanently.** `admin-page.php:1372-1374` clicks
  every `.notice-dismiss` on Esc, firing the AJAX delete at `class-cfzt-admin.php:201-206`.
- **M6. Log injection, CSV formula injection, eviction.** Raw failed-login usernames go into
  the log (`class-cfzt-auth.php:446-448`); `ajax_export_logs` doesn't neutralise leading
  `= + - @`; a hard 1000-row cap means 1000 junk failures evict every real record. (pre-existing)
- **M7. Open-registration footgun.** "Everyone" policy + `auto_create_users` defaulted to yes
  (`provisioner.php:515-517`) = any identity the org's IdPs accept (One-time PIN is on by
  default in new orgs) gets a WP account. The wizard warns about "everyone" but not auto-create.
- **M8. Wizard policy prefill uses the WP admin's email domain** (`admin-page.php:684-689`),
  which denied the first real login on the sandbox because the IdP issued a different domain.
  Add a hint. Also the provisioned policy is named "WordPress administrators" while it admits
  everyone matched and creates Subscribers (`provisioner.php:383`); rename to
  "WordPress login (<host>)".
- **M9. Provenance keys are write-only; no "already provisioned" state, no disconnect.**
  Reopening the wizard shows the token form as if never set up. "Create a second application
  anyway" leaves the first as an orphan. An API timeout after app creation also orphans an app
  with a lost secret.
- **M10. Scope/doc drift.** README:98-99 lists two token permissions; code and template list
  three. README:235-236 documents filters `cfzt_default_role` and `cfzt_user_data` that do not
  exist; `cfzt_new_username` is missing. README links a LICENSE file that doesn't exist.
- **M11. CHANGELOG hygiene.** 2.0.0 is dated 2026-09-30; "Fixed" lists branch-internal bugs
  that never shipped (double-encryption, deep-link keys, provenance, `$setup`), one duplicated;
  the trailing "Important Notes" still warns about SAML signature validation; no 2.0.0 line in
  the version summary; no "Upgrading to 2.0.0" subsection; the `.dev` bullet is stale.
- **M12. `@since 1.1.0` on seven new 2.0.0 APIs** (api.php:12; provisioner.php:18,232,546;
  setup.php:14; plugin.php:437,448).

## Low / Info

- Encryption: AES-256-CBC, key = `wp_salt('auth')`, static IV from `wp_salt('secure_auth')`,
  random 32-byte prefix makes the static IV harmless, no MAC, base64 fallback without OpenSSL,
  salt rotation invalidates stored secrets with no migration. Acceptable for the threat model.
- `protect_session()` starts PHP sessions on every CFZT login; `validate_session_fingerprint()`
  is never called. The "session protection" is inert.
- `CFZT_Login_UI::add_login_button` constructs a new `CFZT_Auth` on every login-page render,
  re-adding `authenticate`/`wp_login` listeners (double log entries). Extra `CFZT_Security`
  instances in backup-codes and the template re-add the header hook.
- Dead code: `CFZT_Cloudflare_API::verify_token()`; `connect()` account_id fallback (JS never
  sends it); `session_duration`/`app_launcher_visible` never sent by JS; one-option auth-method
  select; rewrite-rule flush transient with no rewrite rules left; unused `$auth_method` vars;
  `assets/js/cfzt-admin.js` on disk differs from the `create_admin_js()` generator (two
  sources of truth); empty "Dark mode support" comment stubs.
- Unguarded reads under PHP 8: `$_POST['log']` (backup-codes.php:246), `$options['auto_create_users']`
  (auth.php:340), every `$input[...]` in `sanitize_settings`.
- `sanitize_settings` doesn't whitelist enum values (`login_mode`, `default_role`, …); a bogus
  `default_role` yields users with no role. `team_domain` is admin-controlled SSRF by design.
- Secrets travel through `wp_remote_*`, so `http_api_debug` consumers (Query Monitor) show
  them. Inherent to WP; document it.
- Updater: no signature/hash verification on packages (a compromised GitHub account is RCE on
  every install); release body is the plugin-info text and the updater reads `Tested up to:`
  from it, so write one. Tag must be `v2.0.0`, non-prerelease.
- Template i18n gaps (many hardcoded English strings in admin-page.php; all new provisioning
  strings are correctly wrapped). README project structure omits six files. README features
  don't mention role mapping, domain restrictions, backup codes, logs, import/export.
- Tooltip "It will be encrypted in your database" is only true with OpenSSL.
- Changelog "Changed" username entry says collisions "can never" happen; the counter suffix
  still exists for an exact duplicate login. Say "far less likely".

## Verified sound (all three reviewers)

- All 13 `wp_ajax_*` handlers nonce-check then capability-check; no `nopriv` handlers.
- Setup endpoints: `check_ajax_referer('cfzt_setup')` + `manage_options`; token
  shape-validated and never persisted, logged or echoed; account id regex-validated.
- API client: fixed base URL, `rawurlencode`d path segments, `sslverify` true, timeouts,
  envelope checked, no bodies/headers logged; wizard escapes Cloudflare messages.
- Provisioner: duplicate detection by redirect URI, orphan deletion when credential save
  fails, single-encryption fix correct, provenance survives a form round-trip.
- Redirects go through `wp_safe_redirect` / `wp_validate_redirect`. `$wpdb` queries prepared.
  Templates escape user values. Backup codes: `random_int`, 8 chars over 32, `wp_hash_password`,
  single-use. Secondary-mode password login works again.
- SAML migration logic itself (when it runs) is version-gated, idempotent, falls back to
  secondary mode, drops `saml_*`, raises a persistent notice; OIDC 1.0.4 sites untouched.
- Uninstall removes every option, user-meta, transient and the logs table that 2.0.0 writes.
- `php -l` clean on every file under PHP 8.2; no syntax above the 7.2 floor. Versions are
  consistent (header, constant, changelog). Tags are `vX.Y.Z`.

## Recommended order

1. B1, B2 (auth), B4, H1 (settings integrity), B3 + F14 (upgrade path), H3, H5, H6 (wizard).
2. B5, B6, M10–M12 (packaging and docs). Then a real 1.0.4 → 2.0.0 update on the sandbox
   through the WordPress updater.
3. H2, H4, M1–M9 in a 2.0.x or 2.1.
